# 親機・子機連携の再設計

この文書は Codex サブエージェントによる設計案。Antigravity で指定の Claude Opus 5.5 Medium を起動したが、個人枠の上限（HTTP 429）でレビューは未実施。本番設定・在庫・ハードウェアへの変更は行っていない。

## 現状と課題

- Ubuntu 26 親機、Raspberry Pi 2台、UNO Q 1台。直近の実機確認では親機の監視 API で3台が online、heartbeat を介した既存設定の再送で3台が applied。これは設定適用の確認で、実カード、モーター、払い出しの動作確認ではない。
- 認証・端末登録・heartbeat は `app/api/units.py` の `api_unit_heartbeat`、配置・送信・適用応答は `app/state.py` の `queue_config_update`、`get_config_update_for_delivery`、`acknowledge_config_update` と `app/services/unit_service.py` の `heartbeat_update` が中心。端末側は `unit/unit_client.py` の `send_heartbeat` 内で ACK を次回送信までメモリ保持する。親機再起動には DB の状態が残るが、子機再起動をまたぐ ACK の回復は設計対象。
- HTTPS プロキシ経由の端末が親機に 127.0.0.1 と記録された。従来の設定即時反映と `server.py` の `api_send_unit_command` は保存 IP と推測ポートに依存するため、監視の表示値を到達可能な宛先として扱わない。
- UNO Q は Sony NFC を起動診断で検出しているが、`unit/unit_client.py` の実行時プラットフォーム判定で PC 扱いとなり、読み取りループを起動しない。Linux 側の USB NFC と、MCU 側のモーター・センサーは別の検証対象。

## 接続方式と登録

子機起点の既存 HTTPS heartbeat を正規経路とする。親機が子機の登録 IP に接続できなくても、設定配信と結果確認が完結する構成を目標にする。互換期間中は現行の JSON フィールドと認証を維持する。機能の追加は任意フィールドから始め、旧子機が未送信なら「未報告」として表示する。

初期段階は既存の子機名と端末ごとの認証情報を維持。次段階で親機が発行する不変 ID と表示名を分ける。新規登録では期限付きの要求と管理者承認を使い、実機の ID と設置場所を照合する。承認、拒否、認証情報の更新は監査記録に残す。既存3台への移行では再登録を要求せず、現在の登録に ID を割り当てる。

監視用にプロキシ接続元と子機申告アドレスを分離する。転送ヘッダーを採用する場合は信頼するプロキシを明示し、直接到達した要求からの同名ヘッダーは使わない。自己申告アドレスには出所を明記し、親機のリクエスト先や認証判断に流用しない。送信先を推測する従来の経路は利用箇所を洗い出してから縮退させる。

## 管理画面との契約

| 項目 | 表示する状態 | 判定基準 |
|---|---|---|
| 到達性 | オンライン、遅延、オフライン、不明 | 親機で認証済み heartbeat を受信した時刻と期待間隔 |
| 業務状態 | 利用可、停止中、要点検 | 管理者の利用設定、在庫、対応能力、故障状態。端末の応答有無は別表示 |
| 機器能力 | NFC、モーター、センサーそれぞれの未報告、利用可、利用不可 | 実行時プローブと短い理由コード。利用可否の最終判断は端末でも行う |
| 設定 | 保留、送信済み、適用済み、拒否、再起動待ち | 更新 ID・版、報告版、適用応答、理由コード、経過時刻 |

親機の `/api/v1/admin/units/monitor` と `get_unit_monitor_dashboard` を表示の入口にする。業務画面には対応が要る機器と理由を載せ、端末詳細で設定・時刻・診断履歴を確認できるようにする。通信できても UNO Q の払い出しを利用可能とは表示しない。旧端末の能力が未報告の場合は既存の業務動作を保ち、能力を推定して表示しない。秘密、カード UID、ログ全文は監視一覧に返さない。

## 設定と操作

1. 親機は端末と管理者の権限に応じて編集項目を限定し、現在の適用版を基準として受理する。並行編集で基準版が変わっていれば競合を返し、現状態を再表示する。モーターや配線に関わる変更は通常項目と別に扱う。
2. 子機は受信した版、更新 ID、機器固有の制約を検証する。既存 `apply_remote_config` の候補検証を活用し、実行中の設定を変更する前に検証と原子的な保存を済ませる。再起動が必要な設定は、再起動後の検証が成功した時点で applied とする。失敗時は直前の正常設定を復元し、理由と版を送る。
3. 適用結果は端末に永続化する。応答消失や再起動後も同じ ID の結果を返し、同じ版を再適用しない。親機側は認証済み ID と端末・版を照合し、古い応答で最新状態を上書きしない。ロールバックは履歴から以前の値を選ぶ新しい版として配信する。
4. オフライン中の設定は未適用のまま表示する。モーター試験や払い出しは設定キューに入れない。将来の実機操作は許可された操作と対象能力を検査し、短い有効期限、要求 ID、明示的な現地準備を要件とする。応答不明の動作命令は自動再送せず、現地状態を確認する。既存オフライン運用は `unit/offline.py` の `OfflineStore`・`OfflineSync`、払い出し記録は `app/services/dispense_service.py` の認可・結果処理を維持する。新しい状態表示で在庫や履歴を書き換えない。

## UNO Q の段階導入

- USB NFC の検出を実行基板の判定から分離し、Linux 用リーダー処理を Raspberry Pi と共用できる形にする。既存の UID 処理を再利用し、テスト用カード・試験環境で読み取りを確認する。業務払い出しは未許可のまま。
- MCU の通信方法、ファームウェア版、配線、センサー有無を現物で確認してから、`unit/hardware_controller.py` の既存 `HardwareController` に連携するアダプターを設計する。カード読み取りの成功をモーターの動作保証に使わない。MCU 非応答時は動作命令を拒否し、電源断、再起動、通信断で自動的に動作再開しないことを現地試験で確認する。

## 実装順と受け入れ条件

| 段階 | 実装 | 受け入れ条件 |
|---|---|---|
| 1 | 任意の診断項目と監視表示、テスト用 fixture。既存制御経路を保持 | 現行3台の heartbeat と設定読み出しに互換性がある。旧子機は能力未報告。親機からクライアント由来のアドレスへ通信しない。在庫・モーターに書き込みがない |
| 2 | ACK の永続化、版競合の扱い、設定の失敗理由。Uno Q 上で既存の 30 秒設定を同値で再送して試験 | 親機・子機再起動と応答消失を挟んでも同じ更新を重複適用しない。エラー理由を画面で確認できる。Uno Q で確認後、Raspberry Pi を1台ずつ更新 |
| 3 | UNO Q の NFC 読み取り、対応能力の表示 | 試験カードで読み取り・検証ができる。抜線時に故障表示し、再接続を確認できる。現行 Raspberry Pi のカード経路に回帰がない |
| 4 | MCU 連携と現地動作試験 | 期限切れ・重複・非対応・通信断で意図しない動作がない。センサーの結果と払い出し記録を現地試験で照合する |

段階1は適用フラグを切れば旧表示へ戻せる形にし、DB 変更が必要なら nullable の追記に限定する。段階2以降は実機1台でログと状態を確認してから次へ進め、問題時は子機の直前のリリースと設定へ戻す。旧端末の比率と設定 ACK の実績を確認してから、互換経路の廃止を判断する。
