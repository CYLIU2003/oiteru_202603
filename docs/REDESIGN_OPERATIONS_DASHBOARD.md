# 親機の業務画面の再設計

## 画面の役割

親機の `/admin/dashboard` を、補充・障害対応・利用者対応の入口にする。トップ画面では優先度、対象、次の操作を確認できる。各操作は今の画面へつなぐ。

| 画面 | 主な利用者と作業 |
|---|---|
| `/admin/dashboard` | 現場担当が在庫切れ、接続途絶、進行中の保守を確認し、対象の画面に進む |
| `/admin/operations` | 現場担当が入出庫、在庫調整、保守チケットを扱う |
| `/admin/units` / `/admin/unit_detail/<uid>` | 機器担当が受信時刻、通信、機器の機能、設定反映、登録要求、関連ログを確認する |
| 利用者・履歴・設定 | 利用者対応は既存の利用者一覧・履歴へ、システム設定、バックアップ、復元は保守メニューへ |

役割は画面の利用場面を表す。既存の管理者認証と操作権限を継承し、新たな権限区分の追加は別の変更として扱う。

## 画面構成

```text
オイテル  [業務トップ] [運用管理] [子機監視] [利用者・履歴]
設置場所 / 親機名                               最終取得 14:32:10 [更新]
［補充が必要］  ［通信を確認］  ［未完了の保守］  ［承認待ち］

対応すること                        子機の状態
緊急度  対象    内容       次の操作   機器   通信     在庫   設定   機能
要確認  1号機   在庫 0     [補充]     1号機  オンライン   0    適用済
要確認  子機A   最終受信…  [詳細]     UNO Q  オンライン   —    適用済  監視・設定
                                  [子機監視を開く]

利用者対応 [利用者一覧] [利用履歴]     運用設定 ▾
```

- デスクトップでは対応一覧と子機状態を横並びにする。タブレットでは、件数、対応一覧、子機状態、補助リンクの順に縦積みにする。子機行は狭い画面でカードへ変形し、名前、状態、主要操作が一目で読めるようにする。
- 対応一覧は既存監視のアラートを使う。子機単位の詳細を開けば関連する理由とチケットが分かる。未承認機器は登録要求から扱い、在庫の補充対象には含めない。
- 実排出数は集計開始日時を明示した参考情報に下げる。機器数の数字には対象範囲を示し、現場3台と、DBに残る別機器を混同しない。初期段階は全登録機器を対象にし、現場グループを導入する場合は管理上の指定をデータとして持たせる。
- 自動登録状態は利用者対応の近くへ移す。ホストIDやDB種別は保守情報に置く。状態は短い文言とアイコンで伝え、色だけに依存しない。
- トップのボタンは対応先へのリンクにする。払い出し、モーター操作、設定一括変更、復元の実行はトップに置かない。

## 監視との接続

1. `server.py::admin_dashboard` と `templates/admin_dashboard.html` から始め、既存の `app/services/unit_service.py::get_unit_monitor_dashboard` と `app/api/units.py::api_unit_monitor_dashboard` を監視の共通ソースにする。
2. 初期表示は管理者セッションを確認したうえで概要をサーバー描画する。更新は `GET /api/v1/admin/units/monitor` の `summary.checked_at`、`summary.poll_interval_seconds`、`units`、`pending_units`、`alerts` を使う。監視カード・アラートの表示に必要な範囲のみ描画する。負荷が目立つ場合はログや詳細設定の読込を共通サービスのオプションにし、判定は共通のまま保つ。
3. 内部リンクの対象は承認済み機器なら `UnitMonitorItem.id`、承認待ちなら既存の `unit_name` を用いる。Tailscale Serveを通した観測アドレスが `127.0.0.1` になる場合があるため、IPで機器を照合しない。表示用IPの出所を診断に残す。
4. `connection_status`、`last_seen`、`stock_status`、`config_sync_status`、`hardware_telemetry_status`、`mcu_status` は独立した事実として表示する。オンラインはheartbeat受信を意味する。設定は既存の `pending → delivered → applied` と失敗を表示する。UNO QがPCモードなら監視・設定のみ利用できることを明示し、NFCやMCU・モーターの準備完了を表示しない。未知機種も、機器プロファイルや実測結果の裏付けがなければ機能は「未確認」とする。
5. 運用のチケットや在庫移動の操作は `app/api/operations.py` の既存フォーム/APIを再利用する。通信切れの判定は監視サービスに集約し、運用側の固定閾値と二重に数えない。管理者セッション、既存CSRF検証と操作監査を維持し、APIデータの動的描画はテキストとして扱う。

### 取得失敗時

- 初回取得中は読み込み表示、正常に取得して対象ゼロなら空状態。未取得を件数ゼロとして表示しない。
- タイムアウトや5xxでは直近の成功データを「更新できません・前回取得時刻」と表示し、機器が一斉にオフラインになったように見せない。一定時間後には「古い情報」と表示する。
- 401では自動更新を止め、再ログインへの導線を出す。通信回復時は同じ画面で再取得できる。
- ポーリングは表示中だけ実行し、再取得を重ねない。古い結果で新しい表示を上書きせず、キーボードのフォーカスも移動させない。

## 実装順と合格条件

1. 業務トップに対応一覧、子機概要、既存業務リンクを追加。デスクトップとタブレットで、在庫切れ、オフライン、保守、承認待ちの対象に到達できることを確認する。
2. 監視と業務トップで、同一のスナップショットなら機器・件数・受信時刻が一致することを確認する。0台、登録待ちのみ、混在、通信停止から復帰、監視API失敗、セッション期限切れを用意する。
3. 実機確認では `rp1`、`1号機`、`hirameki-lab-unoq` を名前で照合する。監視と設定確認については3台のheartbeatと、現在値と同じ安全な設定の送信に対するACKを確認する。既存の設定反映待ちがある場合は上書きせず待つ。
4. UNO QのPCモードでは、カードリーダーがUSBで検出されてもNFCアプリ機能を有効と表示しない。払い出しや実モーターの作動を受入試験に含めず、機器の能力確認と実機作動は別の試験にする。
